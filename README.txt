Парсер вакансий LinkedIn

Проект на Python 3.12/3.13, Django 5.2 и PostgreSQL. Команды Search и Details запускаются независимо. Django Admin управляет запросами и показывает вакансии, компании и результаты прогонов.

Запуск на новом компьютере

Склонируйте репозиторий или полностью распакуйте ZIP. В Windows 10/11 x64 откройте local.cmd. Из PowerShell его можно запустить командой .\local.cmd.

При первом запуске нужен интернет. Скрипт использует уже установленный Python 3.12/3.13, если его находит, либо скачает локальный Python 3.13. Затем скрипт скачает PostgreSQL 17, проверит контрольные суммы скачанных пакетов, установит зависимости в .venv, создаст базу и применит миграции. Права администратора Windows не требуются. При повторном запуске используются локальные файлы и сохранённая база. Обе службы слушают только на 127.0.0.1.

Скрипт один раз создаст администратора Django со случайным паролем и покажет логин и пароль в окне запуска. Браузер откроет список поисковых запросов через страницу входа. Django хранит хеш пароля в PostgreSQL. Если забыли пароль, в новом окне PowerShell из каталога проекта выполните .\.venv\Scripts\python.exe manage.py changepassword admin, подставив свой логин.

В базе появится готовый запрос Python Developer / USA. В Поисковых запросах отметьте его и выберите Запустить поиск Search или Запустить поиск и обработку (Search + Details). Операции запускаются по вашему выбору. Результаты можно скачать в разделе Вакансии. Если в переданном ZIP есть exports/linkedin-jobs-updated.csv, этот снимок предыдущего прогона можно открыть отдельно. Новая база запускается без вакансий.

Для остановки Django нажмите Ctrl+C в окне запуска. Для остановки локального PostgreSQL выполните .\local.cmd stop. Если pgAdmin 4 уже установлен, его можно подключить отдельно по параметрам из .env, включая фактический порт PostgreSQL. Для проверки и запуска парсера pgAdmin 4 не требуется.

Параметры ранее настроенного рабочего каталога

Откройте PowerShell в каталоге проекта и выполните:

.\local.cmd

На ранее настроенном компьютере скрипт использует существующий PostgreSQL и существующего администратора Django. Фактический адрес админки отображается в консоли. Если Windows спросит о завершении пакетного файла, подтвердите.

В установленном pgAdmin 4 зарегистрирован сервер LinkedIn Parser (local). При первом подключении введите значение PGPASSWORD из локального файла .env. При необходимости профиль можно импортировать заново из pgadmin-servers.json через Tools → Import/Export Servers. Роль linkedin_app владеет базой linkedin_jobs. Данные локального PostgreSQL хранятся в .local/pgdata.

В локальной базе сохранён пример поискового запроса Python Developer / USA с ID 1. Таблица вакансий изначально пуста.

Ручная подготовка PostgreSQL через pgAdmin 4

1. Запустите PostgreSQL 14 или новее и откройте pgAdmin 4. Выберите Servers → Register → Server. На вкладке Connection укажите адрес, порт PostgreSQL (обычно 5432), базу обслуживания postgres и роль PostgreSQL с правом создания ролей и баз. Документация pgAdmin 4 (https://www.pgadmin.org/docs/pgadmin4/latest/server_dialog.html)
2. В Login/Group Roles → Create → Login/Group Role создайте роль linkedin_app. Задайте пароль на вкладке Definition и включите Can login? на вкладке Privileges. Оставьте права суперпользователя выключенными.
3. В Databases → Create → Database создайте базу linkedin_jobs и назначьте роль linkedin_app владельцем. Используйте UTF-8.
4. В каталоге проекта создайте виртуальное окружение Python 3.12 и скопируйте .env.example в .env. Укажите PGHOST, PGPORT, PGDATABASE, PGUSER, PGPASSWORD и уникальный DJANGO_SECRET_KEY. Файл .env исключён из Git.

py -3.12 -m venv .venv
$python = '.\.venv\Scripts\python.exe'
& $python -m pip install -r requirements.txt
Copy-Item .env.example .env
& $python -c "import secrets; print(secrets.token_urlsafe(48))"

Для локального запуска задайте DJANGO_DEBUG=1 в .env и выполните:

& $python manage.py migrate
& $python manage.py createsuperuser
& $python manage.py runserver

Откройте http://127.0.0.1:8000/admin/. Для развёртывания установите DJANGO_DEBUG=0, используйте WSGI-сервер и раздавайте собранную командой collectstatic статику через веб-сервер с HTTPS.

Логин администратора Django и хеш его пароля сохраняются в таблице auth_user PostgreSQL. Команда createsuperuser запросит пароль интерактивно. PGPASSWORD в .env относится к подключению приложения к PostgreSQL. Аутентификация Django (https://docs.djangoproject.com/en/5.2/topics/auth/default/)

Search, Details и экспорт

В Django Admin откройте Поисковые запросы, отметьте один активный запрос и в меню действий выберите Запустить поиск Search или Запустить поиск и обработку (Search + Details). Во втором режиме после поиска Details обработает ожидающие вакансии выбранного запроса. Для независимого запуска Details откройте Вакансии → Запустить обработку Details. Действия доступны суперпользователю.

В разделе Вакансии ссылка Скачать все вакансии (CSV) выгружает всю текущую базу вакансий независимо от фильтров и страницы списка.

В разделе Прогоны можно включить Автообновление статуса. Список запрашивает обновлённые счётчики каждые пять секунд, пока вкладка видна. Обновление списка не отправляет новые запросы в LinkedIn и не запускает новый сбор. Сообщения фоновых команд записываются в .local/logs.

Те же этапы можно запускать из PowerShell:

1. В Django Admin создайте активный поисковый запрос, например Python Developer со страной USA. Запомните его ID в списке. Для каждой страны можно создать отдельный запрос.
2. Запустите Search с ID запроса. Пример ниже использует ID 1. Для диагностического прогона доступен --max-pages.
3. Запустите Details, когда требуется обработать вакансии из PostgreSQL. Можно указать --limit. При каждом запуске новая попытка выполняется для статусов pending и retry.
4. Экспортируйте текущий снимок вакансий в CSV.

& $python manage.py search_jobs 1
& $python manage.py detail_jobs
& $python manage.py collect_jobs 1
& $python manage.py export_jobs exports/linkedin-jobs.csv

В pgAdmin 4 записи можно проверить через Databases → linkedin_jobs → Schemas → public → Tables. Основные таблицы: jobs_searchquery, jobs_job, jobs_company, jobs_job_searches и jobs_run. В Django Admin поиск по вакансии работает по заголовку, компании и точному ID источника. Список можно фильтровать по стране запроса, запросу и статусу.

Источник и ограничения

Используйте адаптер только с разрешением на автоматизированный сбор. Условия LinkedIn ограничивают автоматизированное копирование данных. Условия LinkedIn, раздел 8 (https://www.linkedin.com/legal/user-agreement)

Адаптер рассчитан на следующие гостевые ответы HTML:

Search — GET /jobs-guest/jobs/api/seeMoreJobPostings/search (keywords, location, start).
Details — GET /jobs-guest/jobs/api/jobPosting/{id} (идентификатор вакансии).
Company — GET /company/{slug} (путь к профилю компании).

В Search страна передаётся как location. Для US и USA используется United States, для UK — United Kingdom. Имена других стран передаются как введены. Начальный start равен 0. Следующее смещение равно предыдущему плюс количество карточек, включая отдельные карточки, которые не удалось разобрать. Пустая страница завершает поиск, повтор страницы фиксируется отдельно. Search повторно начинает обход с нуля, сохраняя уже закоммиченные страницы и найденные связи.

Для проверки контрактов откройте публичную выдачу в браузере и в DevTools → Network отследите первую выдачу и запрос следующей страницы при прокрутке. Затем откройте карточку вакансии и профиль работодателя, сравните фактические URL и формат ответов с адаптером jobs/linkedin.py. Сохраняйте только обезличенные примеры. Проверка через DevTools не завершилась. Запрос Search и разбор карточек проверены на реальной выдаче прямыми HTTP-запросами. Ответы Details и Company успешно разобраны на тестовых HTML-ответах. LinkedIn ограничил доступ к живой карточке вакансии.

Details извлекает структурированные данные Schema.org, когда они есть, и дополняет их полями гостевой HTML-страницы. Компания связывается с вакансией по каноническому URL профиля, если он доступен. Отсутствующие поля остаются пустыми. Если запрос компании завершается временной ошибкой, данные вакансии сохраняются и запись можно дообработать в следующем прогоне. При отказе в доступе к профилю компании оставшиеся запросы к профилям пропускаются в текущем прогоне, а обработка вакансий продолжается. При недоступности вакансии (404 или 410) сохраняется статус unavailable.

При временных сетевых ошибках предусмотрено до трёх попыток. Для 429 команда учитывает корректный Retry-After до 30 секунд. При более длительном ожидании или отсутствии заголовка команда завершает прогон и сохраняет его причину. Базовый интервал между запросами одного процесса задаёт LINKEDIN_REQUEST_INTERVAL. При одновременных Search и Details учитывайте суммарную частоту запросов.

Хранение и экспорт

PostgreSQL гарантирует уникальность вакансии по ID LinkedIn. Связь многие-ко-многим сохраняет все поисковые запросы, в которых она встретилась. Search обновляет поля выдачи, Details обновляет подробности и статус. Блокировка PostgreSQL ограничивает каждый этап одним активным запуском на базу. Search и Details используют разные блокировки. У прогонов сохраняются причина остановки, счётчики, исходные параметры и время. Если процесс аварийно завершён, запись прогона может остаться в running без времени окончания. При повторном запуске записи из успешно завершённых транзакций сохраняются.

CSV записывается в UTF-8 с BOM, использует точку с запятой как разделитель и содержит одну строку на вакансию. Столбцы включают:

- ID и URL LinkedIn, заголовок и местоположение.
- Описание, даты, занятость, формат работы, уровень, функцию, отрасли, зарплату и ссылку отклика.
- Название, идентификатор и URL компании, сайт, описание, отрасль, размер, адрес, тип, дату основания и специализации.
- Статус, число попыток, время последней попытки, ошибку и массив поисковых запросов со странами.

Вложенные поля сериализуются в JSON. В Excel импортируйте ID как текст, чтобы сохранить точность длинных чисел.

Проверка

Для тестов Django нужна отдельная тестовая конфигурация PostgreSQL. Роль среды разработки должна иметь право создать временную базу test_linkedin_jobs, либо администратор PostgreSQL может подготовить такую базу с владельцем linkedin_app и запускать тесты с --keepdb. Не запускайте тесты в рабочей базе.

& $python manage.py check
& $python manage.py makemigrations --check --dry-run
& $python manage.py test

Тесты проверяют пагинацию, повторные страницы, дедупликацию, восстановление после ошибок, ограничения частоты, независимые блокировки, запуск этапов из админки, вход, фильтрацию и CSV. Django Admin использует штатные HTML-таблицы и формы. Тесты проверяют scope на заголовках, связь label с полями и текстовый статус.

Для нагрузочной проверки создайте в pgAdmin 4 отдельную пустую базу linkedin_benchmark с ролью приложения в качестве владельца:

$env:PGDATABASE = 'linkedin_benchmark'
& $python manage.py migrate
& $python manage.py benchmark_jobs samples/benchmark-synthetic-excel.csv --count 5000
Remove-Item Env:PGDATABASE

Команда пропускает синтетические HTML-ответы через тот же адаптер, Search, Details и CSV. Запуск допускается только в базе с пустыми таблицами проекта. Параметр --count принимает 5000–10000.

Прогон LinkedIn. Запрос Python Developer, страна USA. В PostgreSQL сохранено 1 000 уникальных вакансий. Search получил HTTP 400 на смещении 1 000. Контрольный запуск Details сохранил описания 10 вакансий. LinkedIn вернул HTTP 403 при запросе профиля компании, поэтому оставшиеся запросы профилей пропущены в этом прогоне. В реальной выгрузке (exports/linkedin-jobs-updated.csv) 1 000 строк и 31 столбец. Для всех вакансий доступны названия компаний из поисковой выдачи.

Синтетический прогон. PostgreSQL 17.10, запрос Synthetic benchmark, страна USA. Search добавил 5 000 уникальных вакансий за 11,66 с. Details обработал все 5 000 вакансий и сохранил 50 компаний за 16,06 с. Оба этапа завершились без ошибок. CSV сформирован за 0,59 с и содержит 5 000 строк данных, 2 138 068 байт. Эти замеры исключают сетевые задержки LinkedIn. Синтетическая выгрузка (samples/benchmark-synthetic-excel.csv)
